OpenSidebar architecture atlas

AI browser-agent architecture, separated by concept.

OpenSidebar is a Manifest V3 Chrome extension that wraps an LLM in a grounded browser-agent runtime. The model plans and chooses tools, while the runtime owns browser state, safety policy, execution, verification, persistence, and traces.

Concept 1

Runtime topology

Production OpenSidebar is split across the Chrome side panel, the extension service worker, and content scripts injected into pages. The same React side panel also runs in the overlay test harness through an in-memory UI runtime port.

Why this split matters

  • UI components stay environment-agnostic and use UiRuntimePort.
  • Chrome APIs stay in adapters and production shell code.
  • Content scripts own page snapshots, element tags, and DOM actions.
  • The service worker owns the agent loop, orchestration, provider calls, and traces.

Concept 2

AI role separation

The AI architecture separates fast action execution from planning, verification, and visual interpretation. That makes it possible to keep common tasks cheap while still escalating difficult workflows into more deliberate reasoning.

Role Responsibility Primary evidence
Executor Chooses browser tools during observe-think-act turns. Visible elements, page text, perception, tool outcomes.
Planner Decomposes difficult tasks into scoped nodes. User goal, current page context, tool capabilities.
Verifier Judges whether a node or final goal is actually satisfied. Success criteria, page evidence, executor output.
Perception Adds screenshot-based grounding where DOM is insufficient. Screenshot, tagged elements, prior observations.

Concept 3

Agent loop lifecycle

The executor loop repeatedly observes page state, asks the model for the next tool call, executes the tool, refreshes state, and decides whether to continue. The loop streams model output to the UI but keeps tool execution inside validated runtime code.

Observe DOM snapshot, URL/title, visible elements, perception, and prior tool outcomes.
Act Model returns structured tool calls such as click, type, inspect, navigate, or done.
Verify Runtime checks whether action effects and final completion claims match evidence.
Turn lifecycle one executor cycle
Concept 4

Tool layer and safety gates

Tools are the contract between the model and the browser. The model emits a typed request; runtime middleware validates the request, classifies its risk, applies approval policy, dispatches to service-worker or content-script code, and records the result.

Tool categories

  • DOM interaction: click, type, select, set checkbox, drag, hover, coordinates.
  • Navigation and tabs: navigate, go back, create tab, switch tab, create window.
  • Inspection: page, element, hidden content, tables, filters, charts, catalogs.
  • Browser data: cookies, history, downloads, profile fields.
  • Control flow: done, escalate, clarify, update plan.
Tool dispatch path constrained browser action
Concept 5

Multi-step orchestration

Complex workflows are represented as task nodes. Each node has a scoped objective, observable success criteria, dependencies, tool constraints, assumptions, and handoff artifacts. The scheduler runs only runnable nodes, verifies each node, and retries or reroutes failures with context.

Design rules

  • The planner plans; it does not execute browser tools.
  • The executor handles one scoped objective at a time.
  • The verifier judges the node objective, not the entire full task too early.
  • Plan repair adds missing return/read/report steps when the planner drops them.
  • Parallel hints are conservative and serialize ambiguous shared resources.

Concept 6

Perception and grounding

DOM snapshots are the default grounding layer, but browser pages often hide critical information in canvas, images, modals, charts, styling, or layout. OpenSidebar supports visual grounding so the executor can reason over what the page looks like, not only what the DOM exposes.

Structured perception contract

  • LOCATION: where the agent is.
  • CHANGES: DOM-grounded changes since the prior observation.
  • BLOCKERS: popups, prerequisites, mismatches, and obstacles.
  • VISUAL-ONLY: visible values not present in element text.
  • AFFORDANCES: relevant visible controls and valid tag IDs.
Observation paths DOM plus screenshot grounding
Concept 7

Provider routing and BYOK model stack

OpenSidebar is bring-your-own-key. Settings select a provider mode, and the service worker sends model requests directly to the configured provider. The LLM client handles streaming, tool-call parsing, provider-specific payload shaping, retries, image fallback, and usage telemetry.

Concept 8

Observability, tests, and release gates

Browser agents need traceability because final success or failure is not enough to debug AI behavior. OpenSidebar records traces for model calls, tool calls, tool results, perception, verifier decisions, retries, costs, and run-level events.

How to explain it in an interview

Architecture talking points

System design The LLM is inside a runtime boundary. It chooses typed tools, but the extension validates, executes, records, and verifies browser effects.
Reliability Completion is evidence-based. The agent cannot safely finish just because the model says it is done.
Debuggability Every run is traceable across model calls, tool calls, page observations, perception, verification, cost, and latency.

Balanced caveat: OpenSidebar is an OSS BYOK preview and supervised browser agent. It is demo-ready with release-candidate evidence, but dynamic sites, provider outages, rate limits, cross-origin frames, and custom widgets can still require user supervision or runtime fixes.
