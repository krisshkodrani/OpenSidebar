# LP-29: Cloud session privacy and storage

Status: Approved with edits. Owner Decision Stamp recorded 2026-08-08.

## Summary

Add an optional encrypted cloud store for session metadata and restorable
checkpoint objects. This RFC owns consent, storage, retention, export, deletion,
and account-lifecycle behavior. It does not define checkpoint contents (LP-30),
browser command delivery (LP-31), or durable orchestration (LP-32).

The LLM relay remains content-non-retaining. Session persistence is a separate
service, permission boundary, data category, and user choice.

## Goals

- Let a signed-in user list, pin, export, delete, and later restore explicitly
  cloud-enabled sessions.
- Encrypt session objects independently from provider credentials.
- Make ownership checks, retention, deletion, and failure behavior precise.
- Preserve local-only use for users who do not enable cloud sessions.
- Avoid committing the data model to Temporal or another workflow engine.

## Non-goals

- Synchronizing live Chrome tabs, cookies, authentication state, or browsing
  profiles.
- Uploading local raw traces or existing session history automatically.
- Defining the portable checkpoint payload beyond an opaque encrypted object.
- Remotely granting approvals or weakening local safety settings.
- Using session content for fleet analytics, model training, or support review.
- Deduplicating encrypted objects across users or sessions.

## User model and consent

Every session has one persistence mode:

| Mode                 | Behavior                                                                                                         |
| -------------------- | ---------------------------------------------------------------------------------------------------------------- |
| `local_only`         | No session metadata or checkpoint content is uploaded. This is the default for existing sessions.                |
| `cloud_checkpointed` | In-progress and terminal checkpoints are uploaded under the retention policy.                                    |
| `cloud_archived`     | Same as checkpointed, but terminal sessions remain until explicitly deleted or account retention policy changes. |

The first production release defaults new sessions to `local_only`. A user may
choose a remembered default during onboarding, but that choice is itself a safe
cloud preference and must be shown whenever a session starts. Existing local
sessions are never bulk-uploaded. Importing one requires an explicit per-session
action and preview.

The UI displays `local`, `uploading`, `synced`, `sync_failed`, `deleting`, and
`deleted` states. `sync_failed` never prevents local execution or local
checkpointing.

## Data classification

### Session metadata in PostgreSQL

`CloudSessionRecordV1` contains:

```ts
interface CloudSessionRecordV1 {
  schemaVersion: 1;
  accountId: string; // partition/authorization key; never returned
  sessionId: string; // random UUID, not derived from workspaceId
  title: string; // user-visible, maximum 160 UTF-8 bytes
  mode: "cloud_checkpointed" | "cloud_archived";
  status:
    | "created"
    | "active"
    | "waiting_for_user"
    | "paused"
    | "completed"
    | "failed"
    | "cancelled"
    | "deleting";
  revision: number;
  latestCheckpointId?: string;
  latestCheckpointRevision?: number;
  createdAt: string;
  updatedAt: string;
  lastActivityAt: string;
  completedAt?: string;
  pinned: boolean;
  expiresAt?: string; // application-enforced UTC timestamp
  runtimeVersion: string;
  checkpointSchemaVersion?: number;
  sizeBytes: number;
}
```

Titles may contain user content and therefore receive the same access controls
as checkpoint metadata. List APIs return no prompt excerpt, URL, domain,
screenshot, or tool result.

### Checkpoint index in PostgreSQL

`CloudCheckpointIndexV1` contains only:

- account and session ownership keys;
- opaque checkpoint ID and parent checkpoint ID;
- monotonic revision;
- creation time, runtime version, and checkpoint schema version;
- S3 object version/key generated by the server;
- ciphertext size, plaintext-size bucket, and SHA-256 checksum of ciphertext;
- state `upload_pending`, `committed`, `superseded`, or `deleting`.

It contains no task content or client-supplied S3 key.

### Encrypted checkpoint object in S3

The object body is an authenticated encrypted LP-30 checkpoint envelope. The
object metadata contains only schema version, ciphertext checksum, encrypted
data-key reference, and encryption algorithm version. It must not contain
session titles, URLs, prompts, account email, provider keys, or plaintext tags.

## Explicitly forbidden data

Neither metadata nor checkpoint objects may contain:

- provider credentials, OAuth tokens, refresh tokens, cookies, authorization
  headers, password fields, payment-card data, or browser-profile secrets;
- Chrome tab/window/group IDs or `chrome.storage` keys;
- full DOM snapshots, raw accessibility trees, arbitrary downloads, local raw
  traces, hidden model reasoning, or telemetry envelopes;
- approval tokens or a durable representation that an unexecuted sensitive
  action is authorized;
- account email or federated identity attributes outside Cognito.

LP-30 owns field-level projection and forbidden-field tests for the decrypted
checkpoint payload.

## Lightsail storage design

Use the LP-28 Lightsail service and its `opensidebar` PostgreSQL database, not
the LP-25 telemetry stack. Session tables live in a dedicated schema owned by a
least-privilege application role.

- PostgreSQL `cloud_sessions`: composite ownership/indexes on
  `(account_id, session_id)` and `(account_id, updated_at, session_id)` for
  stable cursor pagination.
- PostgreSQL `cloud_checkpoints`: unique `(account_id, session_id, revision)`
  and checkpoint IDs; row locking and one transaction enforce parent revision,
  commit state, and latest-pointer changes.
- Private versioned S3 bucket with Block Public Access, bucket-owner enforced,
  TLS-only policy, no ACLs, and lifecycle cleanup for expired/deleted versions.
- Dedicated customer-managed KMS key for session data with rotation. It is not
  the credential-vault key.
- The Lightsail instance role may use only the session bucket and session KMS
  key. Separate database roles constrain API and maintenance-worker access.
- No browser client receives AWS credentials. If presigned upload is used, it
  targets one server-generated object key, one content length/checksum, one
  content type, and expires within five minutes; commit still requires server
  validation before the object becomes restorable.

### Encryption envelope

Use AES-256-GCM with a fresh data key and nonce for every checkpoint. Generate
the data key through KMS, bind encryption to this context, and store the wrapped
data key beside ciphertext:

```text
purpose=opensidebar-session-checkpoint-v1
accountId=<Cognito sub>
sessionId=<UUID>
checkpointId=<UUID>
revision=<integer>
```

Decryption supplies the exact same context. The service zeroes plaintext key
buffers where the runtime permits. Plaintext checkpoint content must never enter
application logs, traces, metrics, exception messages, or dead-letter payloads.

Server-side envelope encryption protects storage and supports account recovery;
it is not end-to-end encryption. Product copy must state that OpenSidebar's
session service can decrypt a checkpoint to restore it. Client-side E2E
encryption is deferred because cross-device key recovery is a separate product
and security decision.

## API contract

All routes require an LP-28 access token. The authenticated `sub`, never a
client-supplied account ID, selects ownership.

```text
POST   /v1/sessions
GET    /v1/sessions?cursor=&status=&limit=
GET    /v1/sessions/{sessionId}
PATCH  /v1/sessions/{sessionId}
DELETE /v1/sessions/{sessionId}
POST   /v1/sessions/{sessionId}/export

POST   /v1/sessions/{sessionId}/checkpoints/intents
POST   /v1/sessions/{sessionId}/checkpoints/{checkpointId}/commit
GET    /v1/sessions/{sessionId}/checkpoints/latest
GET    /v1/sessions/{sessionId}/checkpoints/{checkpointId}
```

Rules:

- Mutations require `Idempotency-Key` and `If-Match` session revision.
- IDs are server-generated UUIDs. Arbitrary S3 keys are never accepted.
- List limit defaults to 25 and caps at 100; cursors are signed opaque values.
- Metadata bodies cap at 32 KiB; encrypted checkpoint bodies cap initially at
  10 MiB. Larger content must be omitted or handled by a later attachment RFC.
- `PATCH` may change only title, pin state, and persistence mode. It cannot set
  status, revision, ownership, expiry, or latest checkpoint.
- A checkpoint commit atomically marks the object committed and advances the
  session's latest pointer only when parent and expected revisions match.
- Fetch returns ciphertext through a short-lived signed download or a streamed
  session-service response; clients never receive KMS permissions.
- APIs use `Cache-Control: no-store` and never echo forbidden request fields in
  errors.

## Retention and deletion

Initial defaults:

- Incomplete `cloud_checkpointed` sessions expire 30 days after last activity.
- Terminal `cloud_checkpointed` sessions expire 30 days after completion.
- `cloud_archived` or pinned sessions have no automatic application expiry.
- Upload intents not committed within 30 minutes are abandoned and deleted.
- Superseded checkpoint bodies expire after seven days, retaining the latest
  committed checkpoint and the immediately previous checkpoint for rollback.
- Account deletion immediately revokes access and starts deletion of sessions,
  checkpoint indexes, object versions, preferences, credentials, devices, and
  orchestration state.

Scheduled PostgreSQL maintenance and S3 lifecycle are defense-in-depth cleanup,
not the user-visible deletion mechanism. A deletion worker explicitly
enumerates and deletes all object versions and metadata. It runs as an
idempotent Node worker/cron job initially and may move to Temporal after LP-32.
The public target is access revocation within one minute and physical deletion
within 24 hours; backups follow the separately documented backup expiry and are
not restored for an active account.

Deletion is idempotent. A session in `deleting` cannot accept new checkpoints or
be restored. Partial deletion retries from a durable deletion job without
putting object contents into the job payload.

### Regional residency and backup retention

The limited beta is pinned to AWS `eu-central-1` (Frankfurt). PostgreSQL,
checkpoint objects, KMS keys, encrypted database backups, and restore targets
must remain in that region. Changing region or adding a cross-region replica is
a new owner decision because it changes the disclosed data-residency boundary.

The initial backup policy reuses the LP-28 encrypted shared-host backup path:

- daily PostgreSQL backups retain seven days;
- weekly PostgreSQL backups retain 28 days;
- every backup is encrypted with the offline-held age recipient before upload;
- S3 version deletion is performed by the fixed-prefix pruning job and includes
  non-current object versions;
- checkpoint-object lifecycle never expires the latest object before the
  application retention/deletion job has removed its index and all versions;
- deleted account/session data may remain only in encrypted backups until the
  applicable seven- or 28-day window expires and is not restored into an active
  account.

Before beta, the restore drill must decrypt an uploaded backup using the offline
identity on an isolated replacement database and verify both session metadata
and checkpoint-index rows. An on-host plaintext dump drill alone is insufficient.

## Export

Export produces a user-requested encrypted archive containing session metadata,
the latest compatible checkpoint, schema documentation, and checksums. By
default it excludes superseded checkpoints. The archive is generated into a
one-time private object, downloadable through a short-lived URL, and deleted
within 24 hours. Export must not reveal provider credentials or identity-provider
tokens. A later client-side export format may allow local decryption; v1 export
is an account-authenticated portability operation.

## Failure behavior

- Cloud storage outage: execution and local checkpoints continue; UI reports
  `sync_failed` and retries with bounded exponential backoff.
- Upload succeeds but commit fails: object remains non-restorable and abandoned
  cleanup removes it.
- Commit succeeds but response is lost: retrying the same idempotency key returns
  the committed checkpoint.
- Concurrent devices: only the session revision winner commits; loser receives
  `409 revision_conflict` and must re-read.
- KMS unavailable: fail closed, preserve the previous checkpoint, emit a coarse
  operational error, and never return ciphertext as if it were restorable.
- Corrupt checksum/authentication tag: mark that checkpoint corrupt, fall back
  only to the immediately previous compatible committed revision, and visibly
  inform the user.
- Retention/deletion worker outage: alarm and retry; do not make deleted data
  visible again.

## Operational controls

- Per-account session count, storage bytes, upload rate, and concurrent-export
  limits; hard reject before accepting excess data.
- Account-wide AWS budget plus per-service cost and error alarms.
- Kill switches for new session creation, checkpoint writes, exports, and
  restore reads independently.
- Metrics contain counts, byte buckets, latency, status/error codes, and schema
  versions only. No names, titles, object keys, or account identifiers in metric
  dimensions.
- Access logging omits request/response bodies and authorization headers.
- CloudTrail/KMS audit is restricted to authorized operators with documented
  incident response.

## Rollout

1. Pure schema, projection, encryption, retention, and ownership tests.
2. Local AWS emulator or isolated development stack with synthetic content.
3. Internal accounts with manual delete/export verification.
4. Limited opt-in beta after privacy/store disclosure approval.
5. Controlled production expansion under storage and cost budgets.

Rollback disables new cloud writes first. Existing encrypted sessions remain
readable/exportable/deletable until a migration or user deletion completes.
Never strand data by removing read/delete paths before retention has cleared it.

## Verification and acceptance

- Cross-account and guessed-ID access fails for every route.
- Ciphertext differs for identical checkpoints and fails authentication after
  any mutation or encryption-context mismatch.
- Logs, traces, metrics, alarms, DLQs, and error bodies pass forbidden-content
  canaries.
- Interrupted upload/commit preserves the previous latest checkpoint.
- Revision conflicts and idempotent retries are deterministic.
- Lifecycle tests cover active, terminal, pinned, archived, superseded,
  abandoned, session deletion, and account deletion.
- Export contains the promised data and no credentials or identity tokens.
- Backend outage produces no agent-visible correctness change beyond sync
  status and restore unavailability.
- Infrastructure tests assert private/versioned S3, KMS separation,
  least-privilege instance/database roles, PostgreSQL backup/restore, lifecycle,
  budgets, alarms, and kill switches.
- Privacy policy, onboarding consent, session UI, store disclosures, deletion,
  and export documentation are reviewed together before beta.

## Decision

Status: Approved with edits

Chosen path:

- Add explicit-opt-in encrypted cloud sessions using PostgreSQL metadata on the
  $12 Lightsail host and private S3 checkpoint objects under a session-specific
  KMS key.
- Keep the LLM relay content-non-retaining and keep existing sessions local
  unless individually imported.
- Use append-only checkpoint objects, revision-checked latest pointers,
  application-driven deletion, and the retention defaults in this RFC.

Required edits before implementation:

- LP-30 must define and approve the exact decrypted checkpoint payload before
  production checkpoint writes are enabled.
- Record the backup-retention and regional data-residency values for the target
  AWS account before beta.
- Add schema migrations, transaction/isolation tests, and a full PostgreSQL plus
  S3 restore drill to the implementation evidence.

Non-blocking follow-ups:

- Evaluate client-side end-to-end encryption as a separate recovery/key-sharing
  design.
- Consider separately encrypted attachments only after v1 size evidence.

Do not do:

- Do not upload existing sessions automatically.
- Do not store provider credentials, browser authentication state, raw traces,
  full DOM, reasoning, or approval grants in session data.
- Do not use session content for telemetry, support access, analytics, or model
  training without a separately approved workflow.
- Do not make Temporal a storage dependency.

Evidence required before merge:

- All verification and acceptance items above, including privacy disclosure,
  deletion/export, cross-account authorization, encryption, and failure tests.
