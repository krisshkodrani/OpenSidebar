OpenSidebar Trace Viewer

Observability for harness engineering

The viewer is not just a log browser. It is the place where a concrete failure becomes evidence, repeated evidence becomes a ratchet candidate, and the resulting fix is measured against fleet health.

Core Philosophy

One trace explains a failure.
The fleet explains whether it matters.

Good investigations move between those two views without losing the thread.

Metrics Request volume, tokens, cost, latency, index coverage.
Insights Failure, tool, skill, run, model, and event patterns.
Ratchet Repeated failures converted into harness improvement briefs.

Investigation Loop

1

Start With Fleet Health

Check success rate, tool failure rate, token/cost, latency, and model mix.

2

Pick A Pattern

Use Insights or Ratchet to choose a repeated, expensive, or severe failure mode.

3

Open Evidence

Inspect the sample trace: turns, tools, screenshots, logs, and integrity warnings.

4

Ratchet

Name the harness layer, implement the permanent fix, and measure the pattern again.

Surface Map

Surface Question Behavior
Sessions What happened in one execution? Open a trace and inspect its evidence turn by turn.
Runs How did a broader run behave? Compare sessions grouped by run and drill into outliers.
Insights Where are patterns forming? Aggregate failures, tools, skills, runs, models, and events.
Metrics Is the system getting healthier? Track request count, tokens, cost, latency, and trace index coverage.
Docs How should users think? Teach the workflow directly in the product.

What Good Looks Like

A strong viewer session ends with a sentence like: "This is a tool-layer ServiceNow failure affecting 169 calls; here is a sample trace and the copied ratchet brief."

A weak viewer session ends with: "The model failed again." The viewer should make that answer feel incomplete.
